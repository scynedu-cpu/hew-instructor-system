## 3. 발견 사항 → #003-2로 수정 완료

완료기준 4번을 실제로 재현해보니, 당시 `inviteInstructor()`는 **초대할 때마다 무조건 새 `instructors` row 를 생성**했다(이메일 중복만 검사, 기존 프로필과의 매칭은 하지 않음). #003-1은 "계정 없이 강사 등록(#008-1)" 기능이 생기기 전에 만들어져서, 애초에 "이미 프로필만 등록된 강사에게 나중에 계정을 발급"하는 시나리오를 고려하지 않았던 것.

사용자 확인 후 실제 운영에서 이 흐름(대리입력 먼저 → 나중에 계정 발급)을 쓸 예정이라 **작업지시서 #003-2로 같은 세션에서 바로 수정**했다.

## 4. 작업지시서 #003-2 — 기존 프로필에 계정 연결

### 구현
| 파일 | 내용 |
| :--- | :--- |
| [actions.ts](../src/app/staff/instructors/actions.ts) `inviteInstructor` | `instructor_id`(hidden field)가 넘어오면 **새 `instructors` row 를 만들지 않고** 그 row 를 재사용 — `email`/`name` 만 갱신 후 `app_accounts` 를 그 id 에 연결. 이미 계정이 있는 강사·다른 강사가 쓰는 이메일은 초대 전에 막음. `instructor_id` 없이 호출되는 기존 "신규 강사 초대" 경로는 그대로 유지하되, **동명(同名)의 계정 없는 프로필이 이미 있으면** 중복 생성 대신 안내 메시지로 막음 |
| [staff/instructors/[id]/invite/page.tsx](../src/app/staff/instructors/%5Bid%5D/invite/page.tsx) (신규) | "계정 초대" 전용 화면 — 대상 강사의 성명·이메일을 미리 채워서 보여줌. 이미 계정이 있으면 목록으로 리다이렉트 |
| [invite-form.tsx](../src/app/staff/instructors/invite-form.tsx) | `instructorId`/`defaultName`/`defaultEmail` prop 추가로 "완전 신규 초대"와 "기존 프로필에 계정 연결" 두 경우를 한 컴포넌트로 처리 |
| [staff/instructors/page.tsx](../src/app/staff/instructors/page.tsx) (강사 목록) | "계정 없음" 강사 행에 **"계정 초대"** 버튼 추가(기존 "대리입력" 버튼과 나란히) |

### 검증
GoTrue 초대메일 발송(`inviteUserByEmail`)이 테스트 중 이메일 rate limit 에 걸려, 그 부분만 `createUser`(메일 미발송, #003-1에서 이미 검증된 동일 API)로 대체하고 나머지(실제 코드와 동일한 `instructors` 갱신 + `app_accounts` insert 로직, 이후 실제 로그인)는 그대로 실행해 검증:

1. 대리입력으로 "테스트강사003-2" 생성 → 경력 "연결 테스트 경력" 입력·저장
2. 강사 목록 → "계정 초대" 클릭 → 성명·이메일 미리 채워진 폼 확인
3. 계정 연결 실행 후: `instructors` 테이블에 동명 row가 **1개만**(중복 생성 안 됨), `app_accounts` 가 기존 `instructor_id` 에 정확히 연결됨을 DB로 확인
4. 그 계정으로 실제 로그인 → `/instructor` 화면에 **"연결 테스트 경력"이 그대로 표시됨** 확인
5. 테스트 계정·데이터 전부 삭제로 원복
