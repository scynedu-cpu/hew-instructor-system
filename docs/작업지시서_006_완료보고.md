## 1. 구현 내용

### 1-1. 마이그레이션

| 파일 | 내용 |
| :--- | :--- |
| `20260910000000_add_expired_notified_at.sql` | `instructor_documents.expired_notified_at TIMESTAMPTZ` 추가 (기존 `expiry_notified_at` = 임박 알림, 신규 = 만료 알림) |
| `20260910010000_refresh_document_status_fn.sql` | `refresh_instructor_document_status()` — 전체 서류의 `status` 를 `expires_at` 기준(`instructor_doc_status`, #003 규칙)으로 재계산. 바뀐 행 수 반환. SECURITY DEFINER, service_role 실행 |

### 1-2. 배치 로직 — `src/lib/document-expiry.ts` (`runDocumentExpiryNotifications()`)

1. `refresh_instructor_document_status()` 호출 → 시간이 지나 stale 해진 `status` 자동 갱신 (#003 트리거는 업로드 시점만 계산했음)
2. `status IN ('expiring_soon','expired')` 서류 조회 (강사명·이메일 조인)
3. **임박**: `status='expiring_soon'` 이고 `expiry_notified_at IS NULL` → 담당자 이메일 1통 + `expiry_notified_at=now()` 기록
4. **만료**: `status='expired'` 이고 `expired_notified_at IS NULL` → 담당자 이메일 1통 + `expired_notified_at=now()` 기록
5. **발송 성공 후에만** notified 시각을 기록 → 재실행해도 재발송 안 됨. 발송 실패 시 기록 안 하고 다음 실행에서 재시도
6. 여러 건은 한 통에 표로 모아서 발송 (강사 / 서류 종류 / 만료일 + 시스템 링크)

### 1-3. 이메일 발송 — `src/lib/email.ts`

- **Resend REST API** (`POST https://api.resend.com/emails`), 별도 SDK 의존성 없음
- `RESEND_API_KEY` 미설정 시 실제 발송 대신 로그(`simulated: true`) — 로컬/미설정 환경에서도 나머지 로직(상태갱신·notified기록·멱등성)은 그대로 동작·검증 가능
- 발신: `RESEND_FROM_EMAIL` 또는 기본 `onboarding@resend.dev`

### 1-4. 실행 경로

- `src/app/api/cron/document-expiry/route.ts` — GET/POST. `CRON_SECRET` 있으면 `Authorization: Bearer <secret>`(Vercel Cron 자동 부착) 또는 `?secret=` 검증, 없으면 통과(로컬)
- `vercel.json` — `{ "path": "/api/cron/document-expiry", "schedule": "0 23 * * *" }` → UTC 23:00 = **매일 08:00 KST**
- `src/lib/supabase/middleware.ts` — `/api/*` 는 세션 리다이렉트 대상에서 제외 (라우트가 자체 인증)

### 1-5. 환경변수 (`.env.local.example` 갱신)

| 변수 | 용도 |
| :--- | :--- |
| `STAFF_NOTIFY_EMAIL` | 알림 수신 담당자 이메일 (없으면 알림 스킵, notified 미기록) |
| `CRON_SECRET` | Vercel Cron 인증 시크릿 |
| `RESEND_API_KEY` | 없으면 simulated |
| `RESEND_FROM_EMAIL` | 발신 주소 (선택) |
| `NEXT_PUBLIC_SITE_URL` | 이메일 본문 링크용 배포 URL |

스키마 변경은 `expired_notified_at` 컬럼 추가뿐 — 담당자 이메일은 문서별 저장 없이 환경변수로 관리.

## 2. 완료기준 검증

데모: `seed_doc_expiry_demo.sql` — 김민수 성범죄경력조회동의서(만료 20일 뒤)·이력서(만료 10일 지남)를 stale `status='valid'` 로, 박서연 이력서(정상, 대조군). 오늘 = 2026-09-10.

| # | 완료기준 | 결과 |
| :-- | :--- | :--- |
| 1 | 배치가 `expires_at` 기준으로 `status` 정확히 갱신 | ✅ 1회차 응답 `statusRefreshed: 2` — 김민수 성범죄동의서 `valid→expiring_soon`, 이력서 `valid→expired`, 박서연 이력서 `valid` 유지 |
| 2 | `expiring_soon` 신규 → 담당자 메일 + `expiry_notified_at` 기록 | ✅ `expiringSoon.notified: 1`, DB `status='expiring_soon'` + `expiry_notified_at` 기록됨 |
| 3 | `expired` 신규 → 별도 메일 + `expired_notified_at` 기록 | ✅ `expired.notified: 1`, DB `status='expired'` + `expired_notified_at` 기록됨 (`expiry_notified_at` 은 비어있음) |
| 4 | 연속 2번 실행해도 재발송 안 됨 | ✅ 2·3회차 응답 `statusRefreshed: 0`, `notified: 0/0` |
| 5 | 메일에 강사명·서류종류·만료일자 정확히 포함 | ✅ 임박: "김민수 / 성범죄경력조회동의서 / 2026-09-30", 만료: "김민수 / 이력서 / 2026-08-31" + 시스템 링크 |
| 6 | 과거/임박 날짜 샘플로 정상 발송 확인 | ✅ 위 데모로 확인 |

추가: `CRON_SECRET` 없이 호출 시 `401`.

검증은 `RESEND_API_KEY` 미설정(simulated) 상태로 진행 — 발송 대상·제목·본문은 서버 로그로 확인. 검증 후 `seed_doc_expiry_demo_teardown.sql` 로 원복.
